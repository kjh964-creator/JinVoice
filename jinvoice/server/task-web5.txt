JinVoice 웹 수정 2가지를 해 줘. 승인 없이 진행. 비밀값은 절대 출력하지 마. 기존 서비스는 멈추지 마.

A. 웹소켓(실시간 연결) 고치기 — Caddy
1. D:/0.make/homepage/caddy/Caddyfile 을 Caddyfile.bak-jinvoice-ws-<날짜시간> 으로 백업.
2. /jinvoice/app/* 블록의 forward_auth 127.0.0.1:5090 { ... } 안에 아래 두 줄 추가 (다른 줄은 그대로):
       header_up -Upgrade
       header_up -Connection
3. caddy validate → 통과하면 caddy reload. 실패하면 백업 복구 후 reload, 오류 보고.
4. 지난번처럼 secret_key 로 10분짜리 jv_admin 쿠키를 만들어(값은 출력 금지) wss://imist.co.kr/jinvoice/app/ws/events 에 쿠키 + Origin: https://imist.co.kr 로 연결 → 101 로 열리는지, 5초 유지되는지 보고. (앱 화면은 웹소켓 티켓을 받아서 붙는 방식일 수 있으니, 그냥 붙어서 거절되면 backend 의 ws ticket 발급 API(grep 'ticket' backend/api)를 확인해 티켓을 받아 다시 시도.)
5. 쿠키 없이 wss 연결은 거절(302/401/403)되는지도 확인.

B. 메모리 아끼기
6. D:/0.make/JinVoice-cache/start-jinvoice.ps1 에 환경변수 OMNIVOICE_IDLE_TIMEOUT_S=300 추가 (음성을 5분 동안 안 만들면 모델을 메모리에서 내려놓음).
7. JinVoice 서버 재시작: 3920 포트 python 트리만 종료 → 일반 사용자 환경에서 start-jinvoice.vbs 실행 (지난번처럼 Hermes 환경변수가 섞이지 않게 explorer 를 통해 실행하거나 작업 스케줄러로 1회 실행) → /health 200 확인.
8. 서버 메모리(MB), PC 남은 RAM(MB) 보고.
9. 마지막으로 https://imist.co.kr/ , /app/ , /webhard/ , /jinvoice/ 가 200 인지, /jinvoice/app/ 이 쿠키 없이 302 인지 확인.
